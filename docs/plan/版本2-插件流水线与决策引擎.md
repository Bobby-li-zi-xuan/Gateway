# 版本 2：插件流水线与决策引擎（学习版）

## 1. 学习目标

做完这个版本，你能：

- 理解**插件化架构为什么比堆 if-else 好**（扩展性，面试高频题）。
- 理解“路由决策 = 过滤候选 → 打分 → 排序”的通用框架。
- 学会多目标权衡：延迟、成本、质量、健康怎么一起参与决策。
- 做出“可解释路由”：每次决策都能说清“为什么选它”。

## 3. 用大白话讲：这个版本做了什么

版本 1 的前台只会“随机派单”。版本 2 做两件升级：

1. **把大厅改造成安检流水线**：每个请求过一道道检查岗（插件），每个岗一个职责。以后想加新检查（验票、查违禁品），加一个岗就行，不用拆掉整个大厅（核心代码）。

2. **调度员学会打分选店**：不再只看“谁闲”，而是综合“快不快（延迟）、贵不贵（成本）、好不好（质量）、稳不稳（健康）”打分；如果有特殊规则（领导来了直接去包间），就按规则走（条件路由）。

每次派单后，调度员还写一份“为什么选这家”的记录（打分明细）——这就是简历上的亮点：**可解释路由**。

## 4. 功能模块与实现逻辑

### 4.1 插件框架（安检流水线）

**解决什么问题**：网关能力会越来越多（鉴权、限流、护栏、缓存……），不能每加一个能力就改核心代码。

**实现逻辑**：

- 插件契约：名称、执行顺序、作用域（全局 / 路由级 / 模型级）、五类钩子（决策前、决策后、执行前、执行后、异常处理）。
- 插件注册表：启动时按配置加载插件实例，同名去重；插件实例带独立配置。
- 执行引擎：按“阶段 → 顺序 → 作用域”依次执行。
- 共享上下文 `PluginContext`：携带请求、调用方信息、**信号表**、候选集合、决策结果；插件依次读写，后执行者能看到前面写的。
- 候选收窄语义：插件可以移除候选；**候选被清空 → 请求直接拒绝**（fail-closed），不允许静默回退全量候选。
- 配置校验：插件配置不符合 Schema 时拒绝加载，并给出明确错误。

**为什么这样设计**：

- 核心路由永远稳定，新能力 = 新插件，可以单独测试、单独开关。
- fail-closed 防止策略被绕过：比如“企业客户只能用专用模型”，插件误删候选后回退全量 = 专用策略失效，宁可拒绝。

### 4.2 路由信号（小纸条）

**解决什么问题**：插件之间、插件与打分器之间需要传递信息。

**实现逻辑**：

- 信号 = 结构化键值，如 `language`、`task_complexity`、`budget_remaining_ratio`、`canary_group`。
- 写入点：任务识别器（判断复杂度/语言）、预算插件（版本 4）、金丝雀插件（V2 实现示例插件版本——见第 6 节演示场景 A；版本 6 做生产级金丝雀发布：流量比例 / 对比观测 / 自动回滚，机制基于 V2）。
- 消费方式：打分器根据信号动态调权重——预算余量低时调高成本权重，复杂任务强制质量优先。
- 约束：信号只提供“建议”，最终由策略决定；写入必须幂等（同请求重复执行结果一致）。

**为什么这样设计**：LiteLLM 的 Router Plugins 也用同一套思路（RoutingContext.signals），这是“决策可扩展”的关键。

### 4.3 Filter Chain（五道关卡）

**解决什么问题**：打分前先缩小范围，别给明显不合适的候选打分。

**实现逻辑**（按顺序执行，任一道可淘汰候选）：

1. 能力过滤：请求要流式，实例不支持就淘汰。
2. 可用性过滤：不健康、渠道停用、冷却中（版本 3）的实例淘汰。
3. 策略过滤：令牌/租户的模型范围、模型分组限制。
4. 预算过滤：超出预算的候选淘汰或降权（版本 4 接入）。
5. 插件信号过滤：金丝雀分组等插件信号收窄。

过滤链本身也是可插拔的：加规则 = 加插件，不改核心。

### 4.4 Scorer（打分器）

**解决什么问题**：候选都合格，到底选哪个？要做多目标权衡。

**实现逻辑**：

- 四个因子：延迟（实时 EWMA 值）、成本（单价 × 预估 Token）、质量（静态配置，插件可覆盖）、健康（错误率/熔断状态）。
- 实时状态追踪（ModelStateStore）：延迟与健康因子来自实例实时状态，用**单数字指数滑动**在线更新，不存历史样本：
  - EWMA 延迟：`ewma_new = α × 本次延迟 + (1 − α) × ewma_old`；α（配置 `ewmaAlpha`）大则跟手、小则平滑，旧样本影响力按 (1−α)ᵏ 指数衰减。
  - 错误率衰减：成功时不产生错误样本，只把旧错误率按 `(1 − errorAlpha)` 衰减趋向 0（失败时向 1 滑动，公式对照）；语义是"近期错误记忆的衰减指数"，不是严格计数。
  - 原子更新：`ConcurrentHashMap.compute` 保证读-改-写原子，并发记录不丢更新；首次访问用配置 `latencyProfileMs`（缺省 1000）初始化。
- 先归一化到 0~1（因子量纲不同，不能直接相加）。
- 权重向量由策略提供：延迟优先 / 成本优先 / 质量优先 / 均衡；权重和必须为 1，加载时校验。
- 动态调权：执行前读信号，按规则调整权重。内置两条规则（**最小演示集**，各覆盖一种信号来源）：
  - `task_complexity=COMPLEX` → 质量权重 +0.2（从 latency/cost 各扣 0.1）——**请求侧**信号，由复杂度识别插件写入；
  - `budget_remaining_ratio < 0.3` → 成本权重 +0.2（从 quality/health 各扣 0.1）——**系统侧**信号，版本 4 计量写入（当前为预留规则，无写入方时不触发）。
  - 规则守恒：每条规则净变化为 0（+0.2 = 两处各 -0.1），组合命中时权重和仍为 1；扣减用 `max(0, v)` 钳制防负，调整后仍归一化兜底。
- 打分明细：每个候选记录“原始值、归一化值、权重、加权结果”，随路由日志输出。

**为什么这样设计**：可解释性 = 每一步都有记录，这是本项目相对开源项目（多单指标或纯规则）的差异化。调权规则只内置两条，是因为**两层策略分工**：配置层（4.6 策略管理）管“选策略、配权重”，信号层只管“运行期微调”——机制演示够用；新增维度（时段、用户等级、业务线等）走 4.6 的条件规则扩展，不在 Scorer 堆 if（每条规则都要配套信号写入方，没有写入方的规则就是死代码）。实时状态用单数字指数滑动（EWMA）而非简单平均：O(1) 内存、旧样本自动衰减、在线更新无历史负担。

### 4.5 Scheduler（调度器：出方案）

**实现逻辑**：

- 默认策略：按综合得分排序 → 得分最高为主选，其余按序组成降级链（版本 3 使用）。
- 加权随机策略：同分或不分场景按渠道权重随机（复用版本 1 的转盘算法）。
- 条件路由策略：显式规则（如 `task_complexity=SIMPLE → 只用 mini 模型`），按声明顺序求值，命中即覆盖候选集。
- 输出 `RoutingDecision`：主选 + 降级链 + 策略名 + 打分明细；决策不可变，后续阶段只读。
- 会话亲和（可选）：同一会话尽量命中同一实例；开启时策略变更不立即生效（默认关闭，记录这个 trade-off）。
- ⚠️ 2026-08-10 补充（与设计文档 v3.0 6.3 的策略类型映射）：设计文档列的 5 种策略类型中，`MULTI_OBJECTIVE` / `WEIGHTED_RANDOM` / `CONDITIONAL` 本版本实现为三种策略模板；`FALLBACK_CHAIN` **内建**为各策略的统一输出（主选 + 降级链，见上"降级链"）；`CANARY` 延后至版本 6 4.4 金丝雀发布。

### 4.6 策略管理（打分模板管理）

**实现逻辑**：

- 策略模板 = 类型 + 参数（权重向量、条件规则、随机权重映射）。
- 启动校验：权重和为 1、条件规则引用合法、策略引用存在。
- 运行时查询：模型别名 → 生效策略；为版本 5 热更新预留“版本替换”接口。

### 5.1 LiteLLM Router Plugins（本项目插件框架的直接原型）

**来源**：[LiteLLM 官方博客 - Announcing Router Plugins](https://docs.litellm.ai/blog/router-plugins-on-the-proxy)

**文档要点（整理）**：

插件是什么：任意一个对象，提供 `async run(context)` 方法，接收路由上下文（RoutingContext）并返回它。

RoutingContext 里可以改什么：

| 字段 | 作用 | 本项目对应 |
|---|---|---|
| `candidate_models` | 候选模型列表，**只能收窄（移除）**，不能新增 | `PluginContext.candidates` |
| `signals` | 字典，向下游插件/决策器传递信息 | `PluginContext.signals` |
| `metadata` | 请求元数据（如租户） | `PluginContext.metadata` |

**原文示例（摘录）**：

```python
class CheapFirst:
    async def run(self, context):
        cheaper = [m for m in context.candidate_models if "mini" in m]
        context.candidate_models = cheaper or context.candidate_models
        context.signals["cheap-first"] = {"applied": bool(cheaper)}
        return context
```

**关键行为（原文明确写出，本项目必须复刻）**：

1. **按顺序链式执行**：`router_settings.plugins` 里列出的插件按列表顺序运行，后一个插件能看到前一个插件收窄后的候选池和写入的信号。
2. **只收窄、不扩大**：插件只能从候选池移除模型，不能加回被移除的。
3. **fail-closed**：如果某个插件把候选池清空，请求**直接报错**，不会静默回退到全量候选——“so a policy in the chain can't be bypassed by an earlier one”（策略链不可被绕过）。
4. **作用域**：插件可全局挂载（`router_settings.plugins`），也可只作用于某个自动路由器的 tier（本项目对应“路由级/模型级作用域”）。
5. 配置插件后，会话亲和（session_affinity）会被禁用，保证策略变更即时生效（本项目默认关闭会话亲和的依据）。

**对本项目的启示**：本项目 4.1/4.2 的设计（PluginContext、signals、收窄、fail-closed）就是按这套逻辑写的，开发时对照上面的行为逐条验收即可。

### 5.2 Kong 的插件阶段（phases）

**来源**：[Kong 插件开发文档](https://developer.konghq.com/gateway/latest/plugin-development/pdk/)（概念见 Plugins 章节）

**文档要点（整理）**：

- Kong 插件不是“一个函数”，而是挂在请求生命周期**多个阶段**上的：`access`（请求进入时）、`header_filter`（响应头返回前）、`body_filter`（响应体过滤）、`log`（请求结束后记日志）。
- 同一阶段多个插件按**优先级（priority）**排序执行，优先级数字大的先执行。
- 插件作用域：全局（所有请求）、路由级、服务级、消费者级——作用域越小，生效范围越精确。
- 插件配置通过 Admin API 附加到资源上，配置变更无需改核心。

**对本项目的启示**：本项目插件钩子（决策前/决策后/执行前/执行后/异常）就是 Kong 阶段思想的映射；`order` 字段对应 Kong 的 priority。

### 5.3 Portkey 的策略体系（Gateway Configs）

**来源**：[Portkey 官方文档 - AI Gateway](https://portkey.ai/docs/product/ai-gateway)

**文档要点（整理）**：

Portkey 的所有网关策略都通过 **Gateway Config** 声明，而不是写死在代码里，包括：

| 策略 | 作用 |
|---|---|
| Conditional Routing | 按自定义条件（请求属性、元数据）判断路由目标 |
| Load Balancing | 多个 API Key / 模型间负载均衡，应对上游限速 |
| Fallbacks | 供应商/模型间自动降级 |
| Circuit Breaker | 按策略配置熔断保护与失败处理 |
| Canary Testing | 生产环境金丝雀测试新模型 |
| Automatic Retries | 自动重试策略 |
| Request Timeout | 请求超时处理 |
| Budget / Rate Limits | 预算与限流 |
| Cache | 简单缓存与语义缓存 |

**对本项目的启示**：本项目 Scheduler 支持的策略类型（多目标打分、加权随机、条件路由、降级链、金丝雀）与 Portkey 的策略清单对应；Portkey 证明“策略配置化”是成熟网关的标准做法，也证明我们的策略集合没有漏掉主流类型。

## 6. 演示场景与验收标准

### 演示场景 A：插件零侵入生效

写两个示例插件（复杂度识别、金丝雀分组），通过配置挂载：复杂请求走质量优先候选，金丝雀流量只进稳定候选；全程不改核心代码。

### 演示场景 B：可解释路由

对同一请求分别配置 latency-first 与 cost-first：两份决策日志的主选不同、得分明细不同，日志能说清“为什么选它”。

### 演示场景 C：fail-closed

插件把候选池清空（模拟策略冲突）：请求被拒绝，日志记录“哪个插件在哪个阶段清空了候选”。

### 验收标准

1. 插件框架支持全局/路由级作用域、顺序执行、上下文传递、配置校验。
2. 三类策略（多目标、加权随机、条件）均可配置生效。
3. 打分明细随路由日志输出，内存保留最近 N 条可查。
4. fail-closed 行为有单元测试。
5. 版本 1 全部功能回归通过。

## 7. 新手常见问题

**Q1：插件和 if-else 有什么区别？**
if-else 加一个逻辑 = 改核心代码 + 全部重测；插件加一个逻辑 = 写一个类 + 改配置，核心代码不动，可以单独测试、单独开关。面试官喜欢听这个区别。

**Q2：为什么 fail-closed 不回退全量候选？**
回退 = 策略被绕过。例子：规定“企业客户只能走专用模型”，如果插件把候选删光后系统回退到全量模型，这条安全策略就形同虚设。宁可拒绝，不可绕过。

**Q3：打分权重怎么定？**
没有绝对正确答案，靠配置调。学习阶段用差异明显的权重（如成本 0.8 vs 延迟 0.8）对比演示效果，说明原理即可。

**Q4：打分明细存在哪里？**
先放内存环形缓冲（最近 N 条），版本 5 提供查询接口；面试时可以讲“为什么用环形缓冲”（固定内存、自动淘汰旧数据）。

## 9. 端到端示例（把流水线穿起来）

一个具体请求走完整条流水线，每个步骤的中间状态都是算出来的真实数字，对照 4.1~4.6 各模块阅读。

### 9.1 场景与配置

**请求**（`stream=true` 触发能力过滤）：

```json
{ "model": "qwen",
  "messages": [{"role": "user", "content": "帮我写一段 Java 冒泡排序的代码，要求用递归实现"}],
  "stream": true }
```

**候选 6 个实例**（配置 + 实时状态）：

| instanceId | 渠道 | streaming | context | EWMA延迟 | 错误率 | 质量 | priceIn/Out | weight |
|---|---|---|---|---|---|---|---|---|
| mock-a:qwen-max | mock-a | ✓ | 128k | 900ms | 0.35 | 0.95 | 0.010/0.020 | 1.0 |
| mock-b:qwen-max | mock-b | ✓ | 128k | 400ms | 0.04 | 0.95 | 0.010/0.020 | 1.0 |
| mock-a:qwen-large | mock-a | ✓ | 64k | 800ms | 0.30 | 0.90 | 0.005/0.010 | 1.0 |
| mock-b:qwen-large | mock-b | **✗** | 64k | 250ms | 0.02 | 0.90 | 0.005/0.010 | 1.0 |
| mock-a:qwen-small | mock-a | ✓ | 32k | 500ms | 0.10 | 0.60 | 0.002/0.004 | 1.0 |
| mock-b:qwen-small | mock-b | ✓ | **16** | 200ms | 0.05 | 0.60 | 0.002/0.004 | 1.0 |

**策略配置**（`models[].strategy: cond`）：

```yaml
policies:
  - name: cond
    type: CONDITIONAL
    defaultStrategy: balanced
    rules:
      - when: { signal: task_complexity, op: EQ, value: COMPLEX }
        select: [mock-a:qwen-max, mock-b:qwen-max]     # 规则1：复杂任务 → 只用 max 系
      - when: { signal: language, op: EQ, value: zh }
        select: [mock-a:qwen-large]                     # 规则2：中文 → 用 large（示例）
```

### 9.2 流水线逐步走查

**① 信号写入（beforeDecision 插件）**

- `writeRequiredCapabilities`：`stream=true` → 写 `required_capabilities={streaming}`
- ComplexityRecognizerPlugin：匹配"冒泡排序" → `task_complexity=COMPLEX`
- CanaryGroupPlugin：tenant=acme → `canary_group=stable`

信号表：`{required_capabilities:[streaming], task_complexity:COMPLEX, canary_group:stable}`

**② FilterChain：真实淘汰（6 → 4）**

token 估算（4.4 口径）："帮我写一段 Java 冒泡排序的代码，要求用递归实现" = 19 汉字 + 7 其他字符 → `19 + ⌈7/4⌉ = 21 tokens`

| 关卡 | 判定 | 淘汰 |
|---|---|---|
| capability | 含 streaming 需求 → **mock-b:qwen-large 不支持 → 淘汰**；`21 > 16` → **mock-b:qwen-small 窗口不足 → 淘汰** | −2 |
| availability | 渠道均健康（错误率高只降分数不淘汰） | 0 |
| policy | 租户无范围限制 | 0 |
| budget | V4 才接入 → 放行 | 0 |
| plugin-signal | canary_group=stable 无收窄规则 | 0 |

过滤后候选：`[mock-a:qwen-max, mock-b:qwen-max, mock-a:qwen-large, mock-a:qwen-small]`

**③ 求有效策略**
