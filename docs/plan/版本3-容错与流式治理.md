## 3. 用大白话讲：这个版本做了什么

餐厅可能突然关门、上菜极慢、中途停电。版本 3 给网关装上“应急预案”：

- **打不通再拨一次**（重试）——但注意：对方已经接起来、说了一半，就不能重打（会重复上菜）。
- **等太久就挂断**（分层超时）——拨号、等接听、通话总时长、等下一句话，各有时限。
- **这家不行换备选**（降级链）——版本 2 生成了一份备胎清单，本版本负责按顺序执行。
- **某家店频繁翻车就挂“暂停”牌**（熔断 + 冷却）——避免所有客人都去干等。
- **上菜过程（流式）也要治理**——客人关电视（客户端断开），要通知后厨停菜（取消上游调用），别浪费资源。

版本 3 的核心心法是：**失败不可怕，可怕的是不知道什么失败能重试、什么失败只能放弃。**

## 4. 功能模块与实现逻辑

### 4.1 重试（打不通再拨一次）

**实现逻辑**：

- 触发条件：连接失败、超时、HTTP 429（请求过多，可配）、5xx；4xx 业务错误不重试（重试也没用）。
- **安全边界（本项目关键设计）**：只在“还没收到响应首字节”前允许重试。一旦开始收到数据，失败只能降级或报错。
- 重试优先换候选（用降级链里的下一个），而不是死磕同一实例；同实例重试只在连接级失败时允许一次。
- 退避策略：指数退避 + 随机抖动（`base × 2^n + jitter`），上限可配；429 时优先听上游的 `Retry-After`。
- 每次重试记录原因与去向（`retry_total{from,to,reason}`）。

**为什么这样设计**：重复生成内容比失败更糟。非流式还好，流式一旦吐了半个回答，重试 = 客户端收到两份内容。

**为什么只有“连接失败”允许同实例重试？超时为什么不行？**

一句话原则：**同实例重试必须建立在“确定性信息”上，而不是猜测**。本项目只允许两种同实例重试：

| 情形 | 确定性信息 |
|---|---|
| 连接失败（CONNECTION） | 连接**没建立成功**——失败发生在“请求还没开始”，重试零副作用 |
| 429 + Retry-After | 上游**明确告诉你**“等 X 秒再试”——这是上游的显式指令，不是我们的猜测 |

而超时的信息是“请求发出去了，但不知道上游在干什么”——一个不确定状态。此时重试同一个实例：

1. **火上浇油**：超时最可能的解释是上游忙。你已经等了一个超时窗口，再打一个请求进去 = 叠加负载，可能把“慢”变成“挂”；
2. **重复副作用**：LLM 场景上游可能正在生成内容，重试 = 双份算力、双份账单；
3. **更慢**：同实例重试要再等一个完整的超时窗口，而换候选是立刻换到健康实例拿到结果。

所以超时一律换候选，不赌同一家。至于“超时可能是偶发卡顿”——没错，但偶发卡顿换候选同样能解决（候选是健康的）；持续卡顿则由熔断的慢调用统计与冷却接管：偶发不触发熔断（有最少样本数保护），持续才触发——这套体系天然区分“偶发”和“持续”，不需要靠同实例重试来赌。

> 若确想放开超时的同实例重试：`RetryPolicy` 全部参数可配置，但默认保守——宁可换一家，也不赌同一家。

### 4.2 分层超时（等太久就挂断）

**实现逻辑**：

- 四层超时：连接建立、完整响应、首字节、总时长；流式额外有“空闲超时”（相邻 chunk 间隔上限）。
- 每层独立配置（渠道级默认 + 请求级覆盖）。
- 超时后按“是否已收到首字节”决定走重试还是降级/报错。
- 超时事件进入状态系统（慢调用计数），供熔断和打分使用。

**为什么这样设计**：一个慢上游如果不设超时，会一直占着线程/连接，把整个网关拖垮。分层是为了精确回答“到底卡在哪一步”。

### 4.3 降级链（备胎清单）

**实现逻辑**：

- 版本 2 的 `RoutingDecision` 已经带了按分排序的候选序列，本版本只负责“按序执行”。
- 流程：主选失败 → 链上下一个候选（各自走重试/超时逻辑）→ 全部失败返回 503。
- 每次降级记录事件：从谁到谁、原因（超时/5xx/熔断/连接失败）、耗时。
- 每个候选尝试次数有限（默认 1），整体受总时长超时约束。
- 预留“成本降级”接口：版本 4 的预算插件可通过信号让降级链跳过超预算候选（V4 实际落地为决策层 BudgetFilter 淘汰候选，见《版本4-治理与计量.md》4.4）。

### 4.4 熔断（保险丝/跳闸）

**实现逻辑**（状态机）：

- 三个状态：**关闭**（正常）→ **打开**（快速失败）→ **半开**（放行试探）。
- 关闭态：滑动窗口统计失败率与慢调用比例；失败率超阈值（默认 50%）或慢调用超阈值 → 打开。
- 打开态：请求直接失败（不再访问上游），走降级链；持续一段时间（默认 30 秒）→ 半开。
- 半开态：放行少量探测请求（默认 1 个）；成功 → 关闭并清零；失败 → 回到打开态重新计时。
- 粒度：按“渠道 + 模型”维度独立熔断；状态写入 `ModelState`，版本 2 打分器可见。

**为什么这样设计**：熔断不是“防止失败”，而是“防止失败的代价无限放大”——上游已经不行了，继续傻等只会拖垮网关自己的吞吐。

**滑动窗口是怎么实现的？**（为什么统计“最近 N 次”而不是“从启动到现在”）

旧故障不该永远影响新判断：一个实例 1 小时前挂了 10 次，现在恢复了，累计失败率依然难看——这会冤枉它。滑动窗口只统计**最近 N 次调用**（默认 100 次），旧样本自动过期，新判断只看“最近”。

实现上用的是**环形数组**（`windowSize=100`，两个数组分别记失败与慢调用），这是熔断器的核心数据结构：

- **写入 O(1)**：新样本写到 `index` 位置，写完后 `index = (index + 1) % 100`——取模让下标自动回绕，这就是“环形”；
- **旧样本自动被挤出**：数组填满后，新样本写入的位置正是最旧样本的位置——覆盖即淘汰，不需要搬移任何元素；
- **计数 O(1) 查询**：写新样本前先减去旧位置样本的贡献、再加新样本的贡献（`failureCount` 只增删两个计数），失败率 = `failureCount / filled`，每次查询不用遍历整个窗口；
- **样本不足不熔断**：窗口没填满（样本数 < `minimumRequests`，默认 5）时不触发——防止刚启动时一两次失败就误杀。

**为什么不直接用“时间窗口”（如最近 10 秒）？** 时间窗口需要给每个样本记时间戳或分桶，实现复杂；而“最近 N 次调用”只需一个数组 + 一个下标，**能手写、能讲清**——这是学习项目刻意不引 resilience4j 的理由之一。代价是低流量时 100 次调用可能横跨较长时间、旧故障停留更久，由 `minimumRequests` 与阈值共同缓解。

**两个窗口的“或”关系**：失败率超阈值（默认 50%）**或**慢调用率超阈值（默认 50%）都触发熔断——上游即使没报错，但一直慢到拖垮吞吐，同样应该熔断。

**两个“不进窗口”的边界**：

- 半开态的探测结果**不进窗口**：探测成功 → 直接关闭并清零窗口；失败 → 直接回到打开重新计时。探测是“一次性裁决”，放进窗口反而污染统计；
- 打开态被拒绝的请求**不进窗口**：它们根本没打上游，不是有效样本，记进来只会稀释失败率。

### 4.5 渠道冷却（连续差评就歇业）

**实现逻辑**：

- 每个渠道维护连续失败计数；连续失败达阈值（默认 5 次）→ 冷却，时长可配（默认 30 秒）。
- 冷却中的渠道从候选剔除（V2 合并后过滤链可见；执行层在候选执行前逐候选检查，见详细计划 12.1），到期自动恢复并清零计数。
- 与熔断的分工：熔断按“渠道+模型”更细，冷却按“渠道”更粗；两者独立触发，任一命中即剔除。
- 恢复后第一个请求视为探测：失败则重新冷却且时长翻倍（上限可配），成功则正常。

**为什么这样设计**：借鉴 LiteLLM 的 cooldown 和 New API 的渠道自动禁用——比熔断轻，适合处理“偶发连续失败”，两者配合覆盖不同粒度。

**与熔断的区别**：
- **判定维度**：冷却看连续失败次数（纯失败样本——密集但短暂）；熔断看滑动窗口的失败率 / 慢调用率（失败混在成功里）。“持续”指时间轴而非样本纯度：失败率 50% × 100 次窗口 = 坏样本贯穿整个窗口期，不是闪一下；短时抽风只污染几个样本，失败率根本到不了阈值。
- **互为盲区（为什么必须有两个）**：短时抽风（密集但短）→ 冷却抓，熔断因“最少样本”门槛抓不到；持续不稳定（稀疏但长）→ 熔断抓，冷却对间歇失败无感——50% 失败率下几乎不出现连续 5 败，任何一次成功即清零计数。
- **行为**：冷却 = 软剔除，跳过该渠道继续试其他候选，到期盲恢复 + 探测失败翻倍惩罚；熔断 = 硬判死，该实例直接快速失败不再访问上游（省下必死的超时预算，请求仍试其他候选），恢复靠半开探测验证，正常流量不越过熔断打上游（否则破坏半开试探语义）。
- **粒度**：冷却按渠道（整条渠道抽风），熔断按渠道 + 模型（单模型持续劣化，不误伤同渠道健康模型）。
- **误判代价**：熔断误判最多付 30 秒半开期（探测成功立即关闭）；冷却误判会反复“放行 → 失败 → 翻倍”，且无验证通道。
- **时间线配合**：故障初期（连续失败形态）冷却先兜底；若故障持续，窗口统计样本攒够后熔断接管，半开探测精确治理。



### 4.6 流式代理（边下边播 + 停播处理）

**实现逻辑**：

- 按 SSE 解析上游事件流，逐 chunk 校验并规范化为 OpenAI 分片格式转发。
- 补齐上游缺失字段（`id`、`created`、`usage`）；错误事件转统一错误体后中断流。
- 客户端断开 → 取消上游订阅并释放连接（不浪费上游资源）。
- 下游消费慢 → 通过有界缓冲与流控限制拉取速率（阻塞式下由 IO 与缓冲控制）。
- 每个 chunk 触发计量回调（版本 4 接入 Token 累加），计量失败不影响转发。
- 流结束：正常/异常都输出结束事件；`usage` 缺失时用近似值（版本 4 细化）。

### 4.7 状态系统增强（决策的“实时情报”）

**实现逻辑**：

- `ModelState` 扩展：EWMA 延迟、错误率、熔断状态、冷却状态、慢调用计数。
- 事件源统一：执行结果、超时、熔断转换、冷却进出都写进状态更新管道（单写者，避免并发写乱）。
- 决策读“最近快照”；状态更新频率（如 1 秒聚合）与决策频率解耦。

### 5.1 LiteLLM 的重试 / 超时 / 冷却 / fallback 配置

**来源**：[LiteLLM 官方文档 - Overview / configs](https://docs.litellm.ai/docs/proxy/configs)

**文档要点（整理）**：这些能力全部在 `litellm_settings` / `router_settings` 里声明式配置：

**原文配置示例（摘录）**：

```yaml
litellm_settings:
  num_retries: 3                    # 每个模型名最多重试 3 次
  request_timeout: 10               # 超过 10 秒报超时
  fallbacks: [{"zephyr-beta": ["gpt-4o"]}]        # 主模型重试失败后回退到 gpt-4o
  context_window_fallbacks: [{"zephyr-beta": ["gpt-3.5-turbo-16k"]}]  # 上下文超长时回退
  allowed_fails: 3                  # 模型 1 分钟内失败超过 3 次 → 进入冷却（cooldown）

router_settings:
  timeout: 30                       # 路由层超时 30 秒
  routing_strategy: simple-shuffle  # 可选：least-busy / usage-based-routing / latency-based-routing
```

**文档关键点（原文语义）**：

1. `num_retries`：对同一个模型名（可能多个部署）重试的次数；
2. `fallbacks`：重试仍失败后，整体回退到另一个模型名——这就是“降级链”的原始形态；
3. `allowed_fails`：短时间失败次数超阈值就冷却该模型——这就是“冷却机制”的原始形态；
4. `request_timeout` / `router_settings.timeout`：超时是独立配置项，和重试分开；
5. `routing_strategy: latency-based-routing`：LiteLLM 也支持按延迟路由——证明本项目“把延迟作为打分因子”的方向是对的。

**对本项目的启示**：LiteLLM 把“重试次数、超时、fallback、冷却阈值”全部做成配置项而非硬编码——本项目 V3 的容错参数也应全部可配置（渠道级默认 + 请求级覆盖）。

### 5.2 New API 的渠道失败处理

**来源**：[New API 特性说明](https://docs.newapi.pro/zh/docs/guide/wiki/basic-concepts/features-introduction) / [One API vs New API 对比](https://www.apiseven.com/one-api-vs-new-api)

**文档要点（整理）**：

- 支持**多渠道负载均衡**：同一个模型配置多个渠道，请求按渠道权重分发。
- 支持**失败自动重试**：某个渠道调用失败后，自动切换到其他渠道重试。
- 令牌管理字段：过期时间、额度（超出自动失效）、模型限制、IP 白名单。
- New API 基于 SQLite 存储渠道与令牌数据（本项目 V4 的 H2 是同类思路）。

**对本项目的启示**：

- “渠道失败自动切其他渠道” = 本项目降级链的最简形态；
- 渠道维度的失败处理与模型维度的熔断分开设计（本项目 4.4 与 4.5 的分工）。

### 5.3 Portkey 的熔断 / 重试 / 降级策略

**来源**：[Portkey 官方文档 - AI Gateway](https://portkey.ai/docs/product/ai-gateway)

**文档要点（整理）**：

Portkey 把这些能力全部做成 Gateway Config 里的策略，且**按策略维度**配置：

| 能力 | 文档描述 | 本项目对应 |
|---|---|---|
| Automatic Retries | 自动重试策略（可配置） | 4.1 重试 |
| Request Timeout | 处理无响应的 LLM 请求 | 4.2 超时 |
| Fallbacks | 供应商/模型间 fallback 提升韧性 | 4.3 降级链 |
| Circuit Breaker | 按策略配置熔断保护与失败处理（per-strategy circuit protection） | 4.4 熔断 |
| Load Balancing | 多个 API Key 间负载均衡，应对上游限速 | V1 加权随机 + V3 冷却配合 |

**对本项目的启示**：“熔断按策略配置”说明熔断参数（阈值、冷却时长、半开放行数）应该挂在策略/渠道配置上，而不是写死在代码里——本项目 4.4 的参数全部可配置。

## 6. 演示场景与验收标准

### 演示场景 A：故障注入全景

mock 实例 A 故障率 100%、B 正常：请求自动完成“A 失败 → 重试/降级 → B 成功”，日志与指标显示降级事件。

### 演示场景 B：熔断与恢复

A 故障率 100% 持续 1 分钟：先看到重试降级，随后熔断打开（请求快速失败，不再等超时）；把故障率调回 0，等待半开探测成功，熔断关闭、流量恢复。

### 演示场景 C：流式断连

客户端请求流式输出中途断开：上游调用被取消（mock 侧可见连接释放日志），网关无资源泄漏。

### 验收标准

1. 重试只在安全时机发生（有单测覆盖“首字节后不重试”）。
2. 熔断状态机转换可观测、可恢复。
3. 冷却/自动禁用与恢复符合配置。
4. 流式透传格式正确；客户端断开后上游被取消。
5. 所有容错事件有日志与指标；版本 1（或版本 2）功能回归通过。

## 7. 新手常见问题

**Q1：重试和降级有什么区别？**
重试是“同一目标再试一次”（或同渠道换连接）；降级是“换一个目标”。实际流程常常是：重试用尽 → 降级到下一个候选 → 新候选再走自己的重试。

**Q2：熔断和冷却有什么区别？**
冷却：连续失败 N 次 → 临时禁用（按渠道），到期自动恢复，轻量。熔断：滑动窗口失败率超阈值 → 打开快速失败 → 半开试探（按渠道+模型），更重但更精准。两者配合：冷却管“短时抽风”，熔断管“持续故障”。

**Q3：流式为什么不能随便重试？**
因为客户端可能已经收到一半内容。重试会让客户端收到“前半段 + 从头开始的完整内容”，造成重复与错乱。所以规则是：首字节前可以重试，首字节后只能降级或报错。

**Q4：滑动窗口是什么？**
只统计“最近一段时间”的失败率，而不是从启动到现在的累计值。这样旧故障不会永远影响新判断。实现上常用环形数组存最近 N 次结果。
